# Shahdara Fiber Net — Cloud Portal

This repository contains only the isolated Supabase cloud edition of the Shahdara ISP billing portal. It does not contain the original offline-first app, browser storage, backups, or customer records. The offline app and its Pages site remain separate and unchanged. No customer or business billing data has been entered in this project.

## GitHub Pages deployment

The GitHub Actions workflow tests the cloud app, validates its frontend configuration, builds the Vite app, and deploys only `dist/` to GitHub Pages. It uses the approved non-production project URL `https://qkdsuvmlutkatcqoewkh.supabase.co` and the repository Actions variable `VITE_SUPABASE_PUBLISHABLE_KEY`. That publishable/anon key is public frontend configuration and is embedded in the browser bundle. Never place database passwords, service-role keys, or admin API keys in the repository or build configuration.

## Web app installation

The header's **Install app** button opens the browser's native PWA install prompt when that browser offers `beforeinstallprompt`; otherwise it displays instructions for the current platform. On Android, open this Pages site in Chrome if it was opened inside Cue. On iPhone or iPad, use the browser's **Share → Add to Home Screen** option (Safari is the fallback if the option is absent). This is a browser-managed web app or home-screen shortcut, not an APK download. The manifest and icons use paths relative to the GitHub Pages project subpath. No service worker or offline cache is configured, so installing the portal does not make it available offline.

## Owner access and sign-in

The approved cloud schema is present in the non-production Supabase project, but no organization, owner membership, Auth user, customer, or bill is provisioned. This username-only login change creates no accounts and changes no Supabase Auth or database settings. The initial owner must be provisioned separately with a unique password through the approved secure flow; never ship `admin123` as a live default.

The visible form has only **Username** and **Password**. Staff usernames are trimmed and mapped invisibly to `${username.trim()}@shahdara.local` for Supabase password sign-in. Customer sign-in first uses the protected server broker to resolve the authenticated username to its existing customer mapping. There is no email field, magic-link fallback, or self-service signup in the portal UI. Supabase's current email-confirmation and password policies remain unchanged; an alias alone does not provision or confirm an Auth account.

## Company branding

An authenticated organization **owner** can edit the public company display name, support phone, address, and logo from the Admin **Company profile** section. This display profile is separate from the canonical organization row used for membership and RLS. Customers see only the branding row for the organization linked to their own portal account, along with the provider contact card. Provider contact details do not come from or overwrite `customer_private_details.phone`. Existing customer receipts and the customer’s own existing bills can be printed with the public company identity; printing does not record a payment.

Logos are uploaded to the dedicated public `organization-branding` bucket, limited to PNG/JPEG/WebP and 1 MiB. The browser checks file signatures and decoded dimensions (maximum 4096×4096); storage policies independently check raster MIME metadata, size, and the authenticated owner’s organization folder. SVG and arbitrary remote logo URLs are not accepted. The additive `20261002162113_organization_branding` migration was applied only to the approved non-production project `qkdsuvmlutkatcqoewkh`; it does not alter customer rows. The Pages workflow does not apply database migrations.

Customer invitations are handled by the separately deployed `invite-customer` Edge Function in the approved non-production project. Gateway JWT verification is enabled; the function also validates the exact browser Origin, verifies the caller, checks owner/admin membership in the requested organization, and validates that the customer belongs to that organization. A server-only reservation serializes duplicate and concurrent requests before Auth is called. New requests are limited to 5 per administrator/hour, 3 per email digest/hour, and 20 per organization/hour. The workflow stores only a SHA-256 email digest in its unresolved request row and clears it after linking; rate-limit digest buckets expire within 24 hours. A random request marker plus the same email digest can recover an Auth invite if the link step fails or the function stops between Auth and database updates. Repeating the same customer/email is idempotent and never sends a second invitation; unresolved or conflicting state stops for administrator review. Account linking is performed only by service-role-only database functions, not by browser writes. Errors and responses do not expose the email address or Auth user ID, and the function does not log request PII.

`APP_ORIGIN` and `APP_REDIRECT_URL` are server-only URL settings; the function uses Supabase's hosted server-side `SUPABASE_SERVICE_ROLE_KEY` and does not store that key in this repository, the browser, or Actions. A successful response means the Auth invitation request was accepted (or an earlier request was recovered) and the account link was created; it does not confirm email delivery. No customer invitation email or Auth magic link is sent by the test suite or deployment. The Pages workflow builds and deploys only the browser `dist/` artifact; it does not deploy the Edge Function, create Auth users, send invitations, or apply database changes. Apply `20261002120000_customer_invitation_lifecycle.sql` to the approved staging project and deploy `invite-customer` separately. Do not weaken RLS or use anonymous access as a bootstrap shortcut.

## Read-only customer credentials and live traffic

Customers enter their PPPoE username and a separately provisioned portal password. RouterOS PPP secrets do not provide a safe plaintext-password import path; do not assume or reuse a RouterOS/RADIUS password. The portal has no customer change-password or recovery controls. Accounts whose backend credential state still requires a first-login password change remain blocked from customer data until an administrator completes the approved provisioning/recovery flow. The existing server-side broker, RLS gates, and Auth password policies are not weakened. See [`docs/customer-username-password-auth.md`](docs/customer-username-password-auth.md) for the credential boundary and remaining setup constraints.

The customer dashboard includes a Canvas speed graph. With the real API configured, it polls a fixed customer-only endpoint every two seconds; the server verifies the bearer user, requires exactly one linked portal context, resolves that customer's PPPoE username within the same organization, then permits only a strict RouterOS `/interface/monitor-traffic` one-shot request. It accepts no customer IDs or arbitrary RouterOS command parameters. The UI labels mock readings as demo data. **Ninety customers polling every two seconds would create 45 requests/second and is not supported by the current 10-requests/second and four-in-flight server limits.** A shared sampler/cache or push stream is required before scaling to that load.

The live speed sample is not a billing counter. Current-month consumed data displays **Unavailable** until an authoritative calendar-month usage source exists; cumulative session counters are not presented as monthly usage. Current-month bill status is displayed separately from the usage total. The Node API, RouterOS connectivity, account provisioning, and production/static-site deployment must be configured separately; the Pages workflow only builds/deploys static assets and does not provision accounts or deploy the API. Never put `SUPABASE_SERVICE_ROLE_KEY`, RouterOS credentials, or `PORTAL_RATE_LIMIT_HMAC_KEY` in the frontend or repository.

## Local development and tests

Requires Node.js 20.19+ or 22.12+ and npm.

```sh
cp .env.example .env.local
# Set only the approved project URL and publishable/legacy anon key in .env.local.
npm ci
npm test
npm run build
tests/run-local-customer-auth.sh
npm run test:db
npm run dev
```

`.env.local` is ignored by Git. `npm test` covers synthetic ledger behavior, invitation and username/password Edge Function handlers with mocked clients, branding validation/printing, auth/RLS static security contracts, Supabase client configuration and query adapters, the price-history trigger correction, and the bandwidth-usage security contract. `tests/run-local-customer-auth.sh` initializes a separate ephemeral PostgreSQL 16 cluster, applies the auth migration to synthetic fixtures, tests RLS gates, one-time lifecycle, and throttling, then stops and removes only that cluster; it never connects to Supabase or the existing local PostgreSQL cluster. `npm run test:db` creates a separate disposable PostgreSQL 16 cluster, applies repository migrations locally, runs the organization-branding and customer-bandwidth pgTAP suites with synthetic fixtures, and removes the database and cluster on exit. Neither local runner connects to staging or production. A separate `supabase test db` run requires the Supabase CLI and Docker.

The Phase 1 bandwidth mapping, row policies, and server-only sync contract are described in [`docs/customer-bandwidth-usage.md`](docs/customer-bandwidth-usage.md).

## Admin live PPPoE sessions

The Admin **Active Sessions** panel and Customer live-speed graph use a read-only API when an explicitly configured private backend is available. The GitHub Pages hosted preview is pinned to `VITE_ROUTER_DRIVER=mock`, does not receive a live API base URL, and uses synthetic in-browser telemetry even if a runtime API URL is present. Subscriber discovery and import are also simulated in memory in this mock preview; they do not send subscriber rows to Supabase. Mock preview imports reset when the page is reloaded. Real RouterOS subscriber sync is a separate local-only command; see [`docs/local-router-sync.md`](docs/local-router-sync.md).

For local development, `npm run dev` serves the API through Vite middleware. For a same-origin local Node deployment, run `npm run build` and then `npm start`; that server serves `dist/` together with the API. To run only the separate private API service on a Mini PC, install Node.js 20.19+ or 22.12+, copy the repository, run `npm ci`, configure the server-side `.env`, then start it with `npm run start:api`. The API-only service does not need a frontend build or `dist/`; it listens on `HOST` (default `0.0.0.0`) and `PORT` (default `4173`), so it can be supervised by PM2 (`pm2 start npm --name shahdara-pppoe-api -- run start:api`) or another process manager. Set `CORS_ORIGIN` to the exact privately hosted frontend origin (comma-separated only if there are multiple approved origins); do not use `*`. The Pages preview is forced to mock and is not wired to this API. Keep `VITE_PPPOE_API_BASE_URL` public-only: never place RouterOS or Supabase service-role credentials in frontend configuration.

For a separately operated private API host, live RouterOS mode still requires the explicit server-only `ROUTER_DRIVER=mikrotik` setting and a dedicated read-only account. The GitHub Pages build stays mock-only. For actual local subscriber import, run `scripts/local-router-sync.js` on the laptop that can reach the router; its API-SSL/private-LAN checks, dry-run default, `--apply` gate, and required Supabase owner/admin JWT are documented in [`docs/local-router-sync.md`](docs/local-router-sync.md). The atomic import RPC migration `supabase/migrations/20261007223600_router_subscriber_import.sql` remains unapplied, so real imports stay unavailable until the database owner separately reviews/applies the prerequisite schema and provisions an organization/admin. No migration or import is run by this change.

`/api/admin/pppoe/sessions`, `/api/admin/pppoe/router-health`, and `/api/admin/subscribers/discover` are GET routes; `/api/admin/subscribers/import` is a POST route. Admin routes verify the caller's Supabase bearer token and same-organization `owner`/`admin` membership. `/api/customer/live-traffic` is a GET route scoped to the signed-in customer's single same-organization mapping and uses per-user and per-process request/concurrency limits. Every route sends `Cache-Control: no-store`. Subscriber imports never change RouterOS configuration; repeated usernames already linked in the organization are skipped. Traffic counters are per currently connected PPP session (they can reset on reconnect), not subscriber lifetime accounting; the displayed real-router latency is the RouterOS API round-trip, while the mock fixture reports 5 ms. GitHub Pages continues publishing static `dist/` only; it cannot run the Node API. The browser fallback is synthetic UI data, not a substitute for router connectivity or authorization. PM2 deployment and PR #18 are not changed by these code changes.

## MikroTik sync agent (draft-only)

The `sync-agent-ingest` Edge Function now has a separate RouterOS session-delta contract. The read-only daemon polls `/ppp/active` every 60 seconds and submits keyed per-session counters over verified HTTPS; the prepared `20261008003000_monthly_quota_poller_delta_aggregation.sql` migration defines durable baselines and Pakistan-local month totals. The monthly migration and the FUP package migration remain unapplied, and `SYNC_AGENT_DELTA_SOURCE_CONFIRMED` must remain unset until the schema/function contract is reviewed and deployed. These totals are estimates: a poller cannot recover traffic after the final poll before disconnect, so the quota bar is advisory and never throttles, suspends, or disconnects a router user. In Vite development only, synthetic `shahdara_user_XX` customers show a clearly labeled 64.5 GB / 100 GB example; no live Mini PC or router is connected by this change. See [`docs/mikrotik-sync-agent.md`](docs/mikrotik-sync-agent.md) for the contract and limitations.

This remains a review edition, not a production-ready replacement or full offline-parity port. It has no offline sync/outbox, conflict workflow, multi-organization chooser, operational monitoring/alerting, backup-restore rehearsal, or independent penetration test. Portal username/password access still requires separately provisioned Auth identities and customer mappings; none are provisioned here. Customer portal passwords are independent of PPPoE passwords, and Supabase's existing confirmation/password policies must be tested with the approved project rather than changed by this implementation. The live-speed API and RouterOS connection also require separate deployment and capacity review. Keep the original offline app authoritative until the owner has confirmed access, integration review, and a reconciliation rehearsal are complete.
