# Network device adapter readiness — Phases 11 and 13

This readiness step follows Phase 10's session-only simulation history. The existing `MockDiagnosticsProvider` and deterministic diagnostics already keep live checks unavailable, but they do not define organization-scoped device identity, a customer-to-device resolution rule, or a device-type adapter registry. `src/network-device-registry.js` adds that missing **pure contract**, without connecting or discovering a device.

## Contract in this repository

`createSyntheticDeviceRegistry` accepts only explicitly synthetic, in-memory fixture records. A device has an exact organization ID and device ID, a vendor identifier, a normalized device type, and an explicit connected/disconnected test state. An adapter declares its vendor, supported device types, `read-only` access mode, an allowlisted set of read-only summary capabilities, and a synthetic test state. Customer lookup is permitted only through one explicit mapping in the same organization.

`resolveSyntheticDeviceAdapter` requires exactly one selector: an exact selected device ID, or a customer ID resolved through that explicit mapping. It uses exact identity equality; it does not fuzzy-match, infer topology, select the first router, or fall back from a missing device to a mapping. Zero or multiple device/mapping/adapter matches, disconnected fixtures, and undeclared capabilities fail closed. The unavailable result has a fixed sanitized shape and message, carries no supplied identity, and never includes vendor payloads or secret fields.

A successful result means only that synthetic metadata matched the contract. It is marked `synthetic-fixture-only`; it does not prove a physical connection, perform a live check, expose vendor output, or permit execution. Tests use metadata-only mock descriptors for a MikroTik router, an OLT, a wireless access point, and a generic typed device. No vendor API/client or response parser is implemented. The module is not imported by the application entry point, so the Admin simulator's lazy loading and runtime bundle path are unchanged.

There is still **no connected router, OLT, wireless device, live customer mapping, or LLM** in the current application. The registry adds no UI, inventory or mapping table/field, migration, Supabase operation, RADIUS/API call, credential, customer/financial data, or action capability. Existing simulation history remains session-only and is not an action log.

## Gates before a real connection

1. **User-supplied topology and data design:** provide and separately review the organization/device identity scheme, actual vendor/model and normalized type, device ownership/site boundaries, authoritative customer-to-device mapping source, whether a customer can map to multiple devices, uniqueness/lifecycle rules, and how reassignment or missing mappings behave. Do not create database fields or tables until that design and the required data are supplied.
2. **A real isolated lab target and approved network path:** connect a non-customer test device through an explicitly approved gateway/VPN or equivalent path. Confirm vendor/firmware support, source restrictions, verified TLS, timeouts, and a safe disconnection/recovery path. A private router is not reachable from the static Pages browser by default.
3. **Least-privilege server-side adapter:** separately implement and review an authenticated backend broker that rechecks organization-admin authorization on every request, keeps credentials server-side, uses a dedicated read-only principal, and exposes only the declared capability allowlist. The browser must not receive device credentials or direct access to private management endpoints.
4. **Normalized, minimized result semantics:** define the evidence fields, freshness and timeout behavior, vendor error mapping, and sanitized `available / unavailable` response contract for each capability. Never forward raw vendor responses, credentials, management addresses, subscriber IPs, or customer identifiers to an LLM. No LLM is configured; any future model/provider requires a separate privacy and authorization decision and must not become the source of truth.
5. **Separate data and rollout approval:** any actual inventory/customer mapping schema, Supabase query/write, migration, deployed function, or live adapter requires its own supplied design, focused security and pgTAP coverage where applicable, and explicit authorization before implementation or deployment. Do not enable RouterOS writes, customer/profile changes, RADIUS actions, or other network changes through this read-only contract.

Until these gates are met, use only synthetic fixtures. An unavailable result means no live evidence was obtained; it must not be described as a failed network test, diagnosed customer condition, or restored service.
